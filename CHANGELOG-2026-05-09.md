# Changelog — Snapshot 2026-05-09

## v3.5.198 – v3.5.231

### Visit detail — shared tabbed/card renderer + every-photo display

- **The pattern.** `visit_view` and `review_create` rendered the same visit fields with two slightly different table-based layouts and two divergent copy-pasted JS blocks. Server changes had to be made twice. New shared module [js/visit_card.js](ui_vp/uiVPAtlas/js/visit_card.js) + [css/visit_card.css](ui_vp/uiVPAtlas/css/visit_card.css) drive both pages.
- **Tabs replace stacked tables.** The renderer builds five tabs — `Visit`, `Verify`, `Pool`, `Species`, `Photos` — plus an optional `Reviews` tab when reviews are passed in and `extraTabs` for callers that need to slot extra panels (e.g. the Map tab on `review_create`). Tab order matches the visit_create form's tabs, so an observer who knows the form knows the layout.
- **Cards replace pool-tables.** Every section is a rounded white card with a label/value grid. Species has its own grid of mini-cards, each with adults/eggs/larvae count pills, optional iNaturalist link, and any photos for that species inline. The Pool tab renders vegetation cover as labeled chips ("Trees: 51-75%") rather than a row in a plain table.
- **All visit photos shown.** `Photos` tab fetches via `fetchVisitPhotos()` and renders a responsive grid grouped by species (Pool, Vegetation, Wood Frog, etc.) with a count badge on the tab. Click any thumb → existing `openPhotoLightbox`. Legacy single-photo columns (`visitWoodFrogPhoto`, etc.) are also picked up so old data still surfaces.
- **review_create gains the Map tab as `extraTabs`.** Lazy-init via `onTabChange` so Leaflet only sets up its container when first shown, avoiding the "tab is hidden so map sizes wrong" trap. Mobile flow simplifies from outer Review/Visit + inner Detail/Map (4 panes) to just the data tabs + Map.

### Visit list — count badges (📷 photos · 🐸 species · 📋 reviews)

- **Backend.** [vpVisit.service.js](api_vp/vpVisit/vpVisit.service.js) `getAll` adds two correlated subqueries to the visits SELECT: `(SELECT COUNT(*)::int FROM vpvisit_photos ...) AS "photoCount"` and `(SELECT COUNT(*)::int FROM vpreview ...) AS "reviewCount"`. The latter replaces the previous `EXISTS ... AS "isReviewed"` boolean — `isReviewed` is now derived in the frontend from `reviewCount > 0`, freeing the same query to surface a real number.
- **Frontend.** [explore/visit_list.html](ui_vp/uiVPAtlas/explore/visit_list.html) renders three small badges next to each row's pool ID. Species count is computed client-side from existing visit fields (any indicator species with adults/eggs/larvae > 0, plus presence flags for fairy shrimp / clams, plus "Other Species" when populated). Local drafts show counts derived from `v.formData` and `v.photos`. Badges go green when count > 0, stay gray when zero so empty visits stay readable.

### Service worker — install loop, cooldown cap, and the kill switch saga

This was a multi-deploy cycle. The chronology matters because each fix exposed the next bug.

- **Initial loop trigger.** Some users on the live deploy were stuck reloading every navigation, app-cache overlay flashing every time. Direct cause: when a SW install completes, app.js auto-calls `skipWaiting()` and the page reloads on `RELOAD` broadcast. If `/sw.js` bytes change per request (live CDN quirk, multi-node deploy, etc.), every reload triggers another install → infinite loop.
- **First attempt: per-session cap.** v3.5.210 added a `vpa_sw_reloaded_this_session` sessionStorage flag — once an auto-reload happened, no more for the session. Plus a `?nosw=1` URL kill switch + standalone [/sw-reset.html](ui_vp/uiVPAtlas/sw-reset.html) recovery page that unregisters the SW and wipes caches. iOS Safari since 15.4 supports `:has()` so the recovery UI works in PWA mode.
- **The session-cap was too sticky.** iOS PWAs in standalone mode keep the same `sessionStorage` across backgrounding for as long as iOS keeps the process alive. A flag set during one deploy blocked every subsequent deploy until the user force-quit. Users got stuck on stale versions.
- **v3.5.222 — replaced session lock with 30s cooldown.** [js/app.js](ui_vp/uiVPAtlas/js/app.js) uses `vpa_sw_last_reload_ts` instead. Loops fire reloads sub-second so 30s easily breaks them; normal deploys with any user idle time sail through. Defensively scrubs the legacy session flag on every page load so existing devices unstick automatically.
- **v3.5.224 — removed the kill switch entirely.** The persistent `vpa_disable_sw` localStorage flag (set by `?nosw=1` and the "Reset + disable offline" button on `sw-reset.html`) was making app.js unregister every SW and wipe every cache on every page load whenever it was set. Once a user had tripped it during any debug cycle, offline support was permanently dead for them — find_pool, the home page, every cached page hit the browser's network-failure response. Three days of "why is offline broken" traced back to this. The cooldown fix in v3.5.222 made the kill switch unnecessary; the kill switch's downside was vastly worse than what it protected against. Removed entirely; both `sw-reset.html` and the in-app Reset App now defensively scrub the flag.
- **Reset App in profile dropdown.** [js/profile_icon.js](ui_vp/uiVPAtlas/js/profile_icon.js) — every page's top-right profile menu gets a 🔄 Reset App option (signed-in *and* signed-out, since a stuck user might not be able to log in). Tapping it confirms with a modal, then unregisters the SW, wipes the Cache Storage API, scrubs the legacy SW-disable + reload-loop flags, wipes IndexedDB UI hint prefs (per `UI_HINT_PREF_KEYS` in [js/cache_keys.js](ui_vp/uiVPAtlas/js/cache_keys.js)), and reloads `/explore/` with a cache-buster. Drafts, tracks, caches, and auth are kept. Inlined teardown so it works even if much of the app's JS failed to load.

### Precache validator — build-time guard against blank-screen-offline

- **What it caught.** The original "blank screen offline" bug from v3.5.213 was caused by 8 files that the home page imports but were never added to `urlsToCache.js` — `/js/profile_icon.js`, `/survey/css/visit_queue.css`, `/survey/js/visit_queue_ui.js`, etc. Online they fetched freshly; offline the SW returned 503 JSON for each, the browser tried to parse JSON as JavaScript, the script crashed, the page never finished drawing.
- **Standalone validator.** New [sw-validate.js](ui_vp/uiVPAtlas/sw-validate.js) walks every HTML page in `urlsToCache.js`, follows every `<script src>`, `<link href>`, `<img src>`, and ES `import ... from '...'` to local files, and refuses to pass if any dep is missing. The walker explicitly ignores `<a href>` (those are navigation links, not build-time deps; we exclude admin pages from precaching on purpose).
- **Three places it runs.**
  - [sw-build.js](ui_vp/uiVPAtlas/sw-build.js) — every `node sw-build.js` calls the validator first; a bad cache list never bumps the version or generates `sw.js`. Pass `--skip-validate` to bypass while iterating.
  - [ui_vp/Dockerfile](ui_vp/Dockerfile) — `RUN node uiVPAtlas/sw-validate.js` in the image build, so a docker-only rebuild also fails fast on a bad cache list.
  - [.githooks/pre-commit](.githooks/pre-commit) — runs the validator when any `ui_vp/uiVPAtlas/**` file is staged. Enable with `git config core.hooksPath .githooks`. Bypass with `git commit --no-verify`.
- **Parser hardening.** First validator iteration broke the moment we added a comment with an apostrophe ("doesn't dump") to `urlsToCache.js` — the regex over quoted strings happily ate everything between an apostrophe in a comment and the next quote in real code, silently truncating the parsed list. Fixed by stripping `//` and `/* */` comments before parsing.

### Cache keys — single source of truth

- **The drift bug.** [explore/js/pool_list.js](ui_vp/uiVPAtlas/explore/js/pool_list.js) bumped its IndexedDB cache key from `pool_cache` to `pool_cache_v2` on May 2 to invalidate stale client caches after a `_photoCount` field was added. But [js/pool_data_cache.js](ui_vp/uiVPAtlas/js/pool_data_cache.js) — which `find_pool.html` uses as its offline fallback — was still reading from the old `pool_cache` key. Result: online find_pool worked (API hit), offline find_pool silently failed because the fallback returned empty rows → no pool marker, no compass.
- **The fix.** New module [js/cache_keys.js](ui_vp/uiVPAtlas/js/cache_keys.js) holds every cache key as an exported constant: `POOL_CACHE_KEY`, `VISIT_CACHE_KEY`, `SURVEY_CACHE_KEY`, `PARCEL_CACHE_KEY`, `MAP_SETTINGS_KEY`. Plus `KEEP_ON_USER_CHANGE` (used by `storage.js` to know what survives a user-change wipe) and `UI_HINT_PREF_KEYS` (used by Reset App). `pool_list.js`, `pool_data_cache.js`, `parcels.js`, and `storage.js` all `import` from it. Bumping a key suffix is one line change; drift is structurally impossible.

### Compass orientation prompt — separated from compass mode toggle

- **The collision.** PoolFinder's compass dial had two click handlers: one toggled the simple-arrow / traditional-rose appearance, the other (on iOS) called `DeviceOrientationEvent.requestPermission()`. Both fired on the same tap, so every load-and-tap silently flipped the user's preferred compass appearance.
- **The persistence sub-bug.** v3.5.220 first removed the `poolfinder_motion_pref` IndexedDB write entirely after discovering iOS doesn't persist `DeviceOrientationEvent` permission across page loads — so storing `'granted'` and suppressing the prompt later left users with a static compass they had no way to re-enable.
- **The real fix in v3.5.221.** The prompt is now the tap target. The orange speech-bubble card (wider, with a hand-pointer icon and explicit copy: "Tap this dialog to enable compass orientation. Tap the compass to change its appearance...") owns the `requestPermission` call. The compass dial owns nothing except the simple/rose mode toggle. The `MOTION_PREF_KEY` constant is gone — the prompt always shows on iOS until the user taps it (grants/denies + dismisses) or taps the X (dismisses for the page load only).

### Modal — 2×2 / 1×4 button grid for crowded confirmations

- After Reset App was added to the profile dropdown, the menu had 4 buttons that overflowed the 500px modal on phones. [explore/css/modal.css](ui_vp/uiVPAtlas/explore/css/modal.css) `.vp-modal-buttons:has(button:nth-child(4))` (iOS 15.4+ supports `:has()`) switches the buttons row to a CSS grid: `repeat(2, 1fr)` on phones, `repeat(4, 1fr)` on viewports ≥ 600px. The 4-button case also widens the modal to `max-width: 620px` on viewports ≥ 640px so a 1×4 row has room. 1–3 button confirmations keep the existing flex-row look untouched.
- Button styling inside the grid was hardened separately — the grid cells constrain width, so buttons need `white-space: normal`, `word-break: break-word`, `min-height: 44px`, and tighter padding so wrapped text grows the cell instead of overflowing.

### Home page — Map tab default + auto-GPS for "Near Me"

- [explore/index.html](ui_vp/uiVPAtlas/explore/index.html) — the active mobile tab is now Map (was List). Three sites updated: tab bar `active` class, initial-state assignment, and the breakpoint-crossing handler. Desktop is unaffected (tabs are hidden via CSS).
- After `wireGpsButton`, if the restored `filters.nearMeKm > 0` (user previously turned on the Near Me filter), programmatically click the GPS button. iOS shows the system geolocation prompt the same as a manual tap; if the user previously chose "Allow on every visit", it auto-resolves. If they deny at the OS level, the existing `gps-denied` UI handles it.

### My Visits and Tracks — owner identity refactor

The list silently dropped most of a logged-in user's visits because of name drift, then the underlying data model was refactored to track owner by stable id.

- **The first symptom (v3.5.227).** A user could find a visit by going to its pool but the same visit didn't show up in My Visits. Username mismatch — visit_list was querying `?visitObserverUserName=jLooVCE` (just the handle), but the same person had visits stored under `jloomis` (April, when no handle was set), `Jloomis` (2022 capitalisation), and `jLooVCE` (recent). 11 of the user's visits across 3 different name spellings, query only matched 6.
- **Stopgap (v3.5.228).** Send all known name variants — handle, username, email, plus lowercase folds — as repeated `visitObserverUserName` query params. The API turns repeated params into `IN (...)`, single round trip catches every name.
- **The real fix (v3.5.229) — track ownership by stable id.**
  - **Frontend.** [survey/visit_create.html](ui_vp/uiVPAtlas/survey/visit_create.html) now stores `user.username` (never `user.handle`) in the `visitObserverUserName` field — the username is the permanent identifier; handles are display names that can change. Upload body also includes `visitUserId` and `visitObserverUserId` from `user.id`.
  - **Backend.** [api_vp/vpVisit/vpVisit.routes.js](api_vp/vpVisit/vpVisit.routes.js) and [vpVisitNew.service.js](api_vp/vpVisit/vpVisitNew.service.js) — new `injectAuthUserId(body, jwtUser)` helper stamps `req.user.sub` onto `visitUserId` / `visitObserverUserId` for every `create` / `update` / `createPoolAndVisit` call where the body didn't supply one. Defense in depth: even a forgotten frontend can't ship an unowned row anymore.
  - **Migration 011.** New [011_backfill_visit_user_ids.sql](db_migrate/migrations/011_backfill_visit_user_ids.sql) walks every NULL-id row and matches `visitObserverUserName` / `visitUserName` against `vpuser.username` / `handle` / `email` (case-insensitive). Indexes both id columns since the new visits query keys off them.
  - **visit_list query change.** Switched from the multi-name `IN(...)` stopgap to `?visitObserverUserId=ID` — clean, stable, name-drift-immune. Falls back to surfacing a visible error if the auth_user blob lacks an id.
- **The pre-existing trigger that almost broke everything.** A pre-existing pl/pgsql trigger `set_visit_user_id_from_visit_user_name` was overwriting `NEW.visitObserverUserId` with NULL whenever the name didn't resolve to a `vpuser.username` (it never checked `handle` or `email`). That blew away migration 011's backfill for every row owned by a user-via-handle. **Migration 012** patched the trigger to preserve any caller-supplied id and never derive the name from the id (the latter caused unique-constraint collisions on live where two rows had the same `(visitPoolId, visitDate)` with different observers). Then **migration 013** swapped the unique constraint itself: from the date-and-mutable-name `(visitPoolId, visitDate, visitUserName)` to a timestamp-and-stable-id `(visitPoolId, "createdAt", visitObserverUserId)`. DATE was too coarse — same observer can legitimately visit the same pool morning and afternoon — and keying on a mutable name made every name normalisation a potential collision. With the new constraint the backfill UPDATEs are non-colliding by construction.
- **Migration 012 ate three deploy cycles** because each retry on live failed before exposing the next layer. Final iteration folds the constraint swap, the trigger fix, and the idempotent backfill into one migration; 013 stays as a no-op for any DB that already passed 012.

### Admin pages — Unavailable Offline panel + the SW-disable flag bug

- **Goal.** Four admin pages (`profile`, `users_admin`, `s123_visit_import`, `s123_survey_import`) require a network connection. Navigating to them offline used to dump the user on a generic browser network-error page with no way back.
- **Shared guard.** New module [js/require_online.js](ui_vp/uiVPAtlas/js/require_online.js) exports `ensureOnline({ pageName, backHref })`. When `navigator.onLine` is false it hides every body child except `<header>`, injects a styled "Unavailable Offline" panel with the page name, a Back button, and a Home link, and wires a one-shot `online` listener that auto-reloads when the network comes back. Returns false so the caller short-circuits its init.
- **Wired into all four admin pages** at the top of `DOMContentLoaded`. The four pages are also added to `urlsToCache.js` so the panel itself can render offline.
- **The cascading SW-unregister bug (v3.5.225).** Every admin page had a long-standing line at the bottom: `<script>if (typeof appConfig !== "undefined") appConfig.useServiceWorker = false;</script>`. app.js's existing handling of that flag was to *unregister* the SW for the device — wiping the offline cache for every other page on the device the moment the user visited any admin page. Symptoms: on returning to the home page, the precache install ran again ("cache reloads on every navigation"); going offline after touching any admin page broke every page except whatever was already loaded. The line was removed from all 7 admin pages (`profile`, `users_admin`, `review_create`, `review_view`, `review_list`, `s123_visit_import`, `s123_survey_import`); admin API endpoints already go network-first via `DATA_NO_CACHE_PATTERNS`, so leaving the SW registered doesn't cache stale admin data. app.js was hardened in parallel to *never* unregister the SW based on the config flag — it now skips its own update check on opt-out pages but leaves the registration intact.

### My Visits and Tracks — hide redundant local "uploaded" rows

- After upload, the local IndexedDB copy of a visit is pure cache: the server is authoritative, edits go straight to the API. The list was rendering the local "uploaded" pill *and* also had to dedupe the matching server row out — extra UI noise for nothing.
- View-only filter in `loadAll`: a local row with `status === 'uploaded'` AND `server_visit_id` set AND `photos_uploaded !== false` is filtered out of the merged list. The server row for that `visitId` then renders cleanly as **server**. Locals with `photos_uploaded === false` stay visible because they still represent outstanding work (photo upload failed/pending). No data deletion — local entries remain in IndexedDB, just hidden from this view.
