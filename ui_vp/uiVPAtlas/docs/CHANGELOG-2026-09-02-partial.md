## v3.5.368 – v3.5.369

### Public visit GeoJSON — loadable by ArcGIS Online, and no longer carrying landowner PII

- **The bug.** Pointing an ArcGIS Online Data Pipeline at `GET /visit/geojson` failed with `ADP_102046` — "The file could not be read... content that is incompatible with the specified format." The endpoint itself was healthy: HTTP 200, 10.5 MB of parseable GeoJSON, all 2,069 features Point geometry. The incompatibility was inside the feature properties.
- **The cause.** [api_vp/vpVisit/vpVisit.service.js](api_vp/vpVisit/vpVisit.service.js) builds properties from `vpmapped.*, vpvisit.*, vpreview.*`, which pulled in two values that a flat GeoJSON-to-attribute-table reader has no field type for: `reviewReasons`, a Postgres `text[]` that serialised as a JSON array (`["Lacks indicator species", "Visit data incomplete / inconclusive", ...]`), and `visitLandowner`, a `jsonb` object. The comparable `/mapped/geojson`, which AGOL ingests without complaint, contains no array-valued property at all — that was the distinguishing difference between the two endpoints.
- **The fix — `reviewReasons` is now a comma-delimited string.** `NULLIF(array_to_string(COALESCE("reviewReasons", '{}'), ', '), '')`, so the three-element array above comes across as `Lacks indicator species, Visit data incomplete / inconclusive, Awaiting follow-up visit`, and both NULL and the `'{}'` column default come across as NULL rather than an empty string. Every feature now carries the key, where before it was absent on visits with no matching review.
- **The fix — `visitLandowner` is dropped from the payload entirely.** That JSONB held `visitLandownerName`, `visitLandownerAddress`, `visitLandownerPhone` and `visitLandownerEmail` on 640 of 2,069 visits, on an endpoint that requires no authentication. Only the email was previously removed, by the value-based sweep in [api_vp/_helpers/scrub.js](api_vp/_helpers/scrub.js); name, address and phone went out in full. Both fixes are applied as jsonb operations on the assembled row (`row_to_json(p)::jsonb - 'visitLandowner' || jsonb_build_object(...)`), so the `SELECT *` convenience is kept and no 165-column list has to be maintained by hand.
- **Side effect, an improvement.** Casting to jsonb de-duplicates the `createdAt` and `updatedAt` keys that `vpmapped`, `vpvisit` and `vpreview` each contributed — the response literally repeated both keys three times. Every JSON parser already took the last occurrence, which is exactly what jsonb keeps, so no consumer sees a change in value.
- **Scope.** No UI code reads `/visit/geojson`; the `visitLandowner` uses in [js/visit_card.js](ui_vp/uiVPAtlas/js/visit_card.js) and the survey sync modules come from the regular visit endpoints and are untouched. `/visit/shapefile` is a separate query and is unchanged. `/review/geojson` lists its columns explicitly and never carried either value. **`/survey/geojson` has the same array problem still open** — its `surveyPhotos` `array_agg` will fail an AGOL ingest the same way.
- **Verified.** 2,069 features, `visitLandowner` absent from every one, `reviewReasons` string-or-null throughout, `mappedPoolLocation` the only remaining nested value (and AGOL demonstrably tolerates it, since `/mapped/geojson` carries it too).
- **Note.** `vpmapped.*` still contributes `mappedLandownerName` / `Address` / `Phone` / `Zip5` / `Town` and the free-text `mappedComments` and `mappedlocationInfoDirections` to this endpoint. The curated `ogc.pool_visits` collection added earlier today excludes all of it and remains the safer source for anything published publicly.

## v3.5.367

### Shapefile export — restored in the Docker stack

- **The bug.** `GET /mapped/shapefile` returned `{"name":"Error","message":"/bin/sh: 1: pgsql2shp: not found\n"}`. The sibling `/visit/shapefile` and `/survey/shapefile` endpoints failed identically — they share one helper. Every shapefile download from the Dockerized API had been dead since the Docker cutover.
- **The cause — two independent gaps, both in [api_vp/Dockerfile](api_vp/Dockerfile).** First, the image installed `postgresql-client`, which supplies `psql` for the startup wait script but **not** `pgsql2shp`; that binary ships in Debian's separate `postgis` package, which was never installed. Second, [api_vp/_helpers/db_shapefile.js](api_vp/_helpers/db_shapefile.js) writes to a relative `shapefile/` directory under the app root and neither creates it nor fails usefully when it is absent — and no such directory existed in the image. Fixing only the missing binary would have produced a second, more obscure failure.
- **The fix.** The image now installs `postgis` alongside `postgresql-client`, and creates `/opt/api/shapefile` owned by the unprivileged `api` user the Node process runs as. Apt lists are removed in the same layer so the added dependency doesn't inflate the image more than necessary.
- **Verified.** All three endpoints return HTTP 200 with a valid gzipped tar carrying the complete five-file shapefile set (`.cpg`, `.dbf`, `.prj`, `.shp`, `.shx`) — `/mapped/shapefile?mappedPoolStatus=Confirmed` 108 KB, `/visit/shapefile` 382 KB, `/survey/shapefile` 254 KB.
- **Why it matters.** The shapefile endpoints are the most practical route for pushing VPAtlas data into ArcGIS Online, which cannot consume our API as a live data source and has to ingest an uploaded file.

### OGC API - Features endpoint — live feature access for ArcGIS Online (new)

- **The problem it solves.** ArcGIS Online cannot use the VPAtlas REST API as a live data source. It can only ingest an uploaded file, or *reference* a service speaking ArcGIS REST FeatureServer or OGC API - Features. That is why the AGOL pool layers are hosted copies that go stale until something overwrites them. This is the other option: a standards-compliant feature service AGOL reads through to Postgres on every draw, with no copy to keep in sync.
- **What was added.** A `pg_featureserv` container (`ogc_vp`, image `pramsey/pg_featureserv`) in [docker-compose-vpatlas.yml](docker-compose-vpatlas.yml), serving a new curated `ogc` schema. Two collections: `ogc.mapped_pools` (13,465 features) from [migration 019](db_migrate/migrations/019_add_ogc_features_views.sql) and `ogc.pool_visits` (2,058 features) from [migration 020](db_migrate/migrations/020_add_ogc_pool_visits_view.sql). Reachable in dev at `http://localhost:9010`. No Node code — the API is unchanged.
- **Two independent safeguards, because this endpoint is public and unauthenticated.** pg_featureserv publishes *every* relation its database role can read. First, `ogc.mapped_pools` lists its columns one by one and never uses `SELECT *` — `vpmapped` carries landowner name, address, phone, email and zip, plus free-text columns that can contain them, and all are excluded. `ogc.pool_visits` likewise omits `visitLandowner`, visitor identity, and `visitDirections` / `visitLocationComments`, which describe access routes across private land — its 63 published columns are the ecological payload only. Second, the service connects as a new least-privilege role `pgfs_reader` holding `SELECT` on the curated views only, never on `public.*` base tables. Verified: `/collections` lists exactly the two curated collections and no base tables.
- **Verified working.** Landing page, `/conformance`, `/collections`, `/collections/{id}` and `/items` all return HTTP 200 with correct link relations. `bbox` filtering and WGS84/CRS84 geometry all confirmed — `mappedPoolLocation` is already `geometry(Geometry,4326)`, so no reprojection is involved. A full fetch of `ogc.mapped_pools` returns all 13,465 features in ~7.0 MB; `ogc.pool_visits` all 2,058 in ~3.4 MB.
- **Paging ceiling raised to 50,000, deliberately.** This build of pg_featureserv emits neither `numberMatched` nor a `next` link, so a client requesting more features than the configured maximum receives a silently truncated page with nothing to indicate the shortfall — at the initial 10,000 setting, a full request for mapped pools returned 10,000 of 13,465 and looked complete. `offset` paging does work (`offset=10000` returns the remaining 3,465) but is undiscoverable without a `next` link, so the ceiling is the only effective guard. `PGFS_PAGING_LIMITMAX` is now 50,000 — roughly 3.7x headroom over the largest collection — and carries a comment to raise it before any collection approaches it. `PGFS_PAGING_LIMITDEFAULT` stays at 1,000 so unparameterised requests remain small.
- **Known gap.** `/collections/{id}/items/{featureId}` returns HTTP 500. pg_featureserv derives the feature id from a relation's primary key, and a Postgres view cannot have one; adding a column named `id` was tested and does not help. `/items` with `bbox` and `limit` — what map clients actually use — is unaffected. If AGOL turns out to require the single-feature resource, the fallback is a trigger-maintained table in the `ogc` schema, which keeps a real primary key while staying current on write.
- **Adding more collections later is one view.** [Migration 020](db_migrate/migrations/020_add_ogc_pool_visits_view.sql) sets `ALTER DEFAULT PRIVILEGES IN SCHEMA ogc GRANT SELECT ... TO pgfs_reader`, so a future `vpsurvey` or `vpreview` collection needs only a `CREATE VIEW ogc.<name>` with columns listed one by one and an `ogc_vp` restart. The one hard requirement is documented in that migration: the view must select a base table's geometry column directly — visits, surveys and reviews have no geometry of their own and must join `vpmapped` for `mappedPoolLocation`.
- **Prod override added — it was a deploy hazard without one.** `ogc_vp` lives in the base compose file, and `deploy-prod.sh deploy` runs base + prod together, so prod would have started it inheriting dev's `container_name: ogc_vp` and dev's `9010` host port — both colliding with the dev stack on the same host — plus a `localhost:9010` link base that would break every self/items link an external client follows. [docker-compose-prod.yml](docker-compose-prod.yml) now gives it `ogc_vp_prod` and binds it to `127.0.0.1:9011`, reachable only by nginx on the same host.
- **Published as a path, not a subdomain.** The endpoint is `https://api.vpatlas.org/ogc/…`, added as a `location /ogc/` block in [deploy/nginx-api.vpatlas.org.conf](deploy/nginx-api.vpatlas.org.conf). That avoids a new DNS record, a new certificate, and a second vhost entirely. The trailing slash on `proxy_pass` strips the prefix so pg_featureserv sees `/collections`, while `PGFS_SERVER_URLBASE=https://api.vpatlas.org/ogc` puts it back on every emitted link — verified: `/collections` returns `self -> https://api.vpatlas.org/ogc/collections`. Config passes `nginx -t`.
- **CORS for the OGC path is scoped to that location.** The api vhost pins `Access-Control-Allow-Origin` to `https://vpatlas.org` at server level, which would block ArcGIS Online — its Map Viewer fetches cross-origin from arcgis.com. Because `add_header` in a location replaces inherited server-level directives rather than combining with them, the `/ogc/` block overrides it with `*`. One known caveat is documented inline: the server-level `if ($request_method = OPTIONS)` runs before location selection, so a CORS *preflight* to `/ogc/` would still get the vhost-wide origin. Simple GETs — what OGC clients issue — are not preflighted, so this should not bite; if it does, the fix is to move OPTIONS handling into the locations.
- **The deploy is now self-contained.** Previously, setting `PGFS_PASSWORD` in prod `.env` was *not* sufficient: migration 019 creates `pgfs_reader` with a dev password (migrations are in git and must carry no secrets), so the container would fail authentication and restart-loop after an otherwise green deploy. [Migration 021](db_migrate/migrations/021_set_pgfs_reader_password.sql) closes that gap by reading `PGFS_PASSWORD` at migration time via psql `\getenv` (PostgreSQL 16+; this stack is 17.5) and issuing the matching `ALTER ROLE`. Verified all three paths: the password is set from the environment, `pgfs_reader` then authenticates and reads 13,465 rows, and an unset variable leaves the existing password untouched instead of erroring under `ON_ERROR_STOP=1`. Rotation remains manual — the migration runs once, tracked by filename.
- **`PGFS_PASSWORD` is a required prod `.env` variable.** Enforced twice: `${PGFS_PASSWORD:?…}` in the prod compose override aborts with a named error, and it is added to `preflight_env` in [deploy/deploy-prod.sh](deploy/deploy-prod.sh) so the deploy fails before the remote build rather than during it.
- **Shipped and verified live.** Migrations 019/020/021 applied cleanly on prod, `ogc_vp_prod` came up, and the endpoint answers through nginx at `https://api.vpatlas.org/ogc/`: landing page, `/conformance` and `/collections` all 200, self-links correctly carrying the `/ogc` prefix, and both collections listed. `ogc.mapped_pools` returns all 13,485 features (7.0 MB), `ogc.pool_visits` all 2,203 (3.7 MB), and a bbox subset 4,438. CORS scoping confirmed in production: `Access-Control-Allow-Origin: *` on `/ogc/` for ArcGIS Online, still `https://vpatlas.org` on the rest of the API — the location-level override does not bleed. `https://vpatlas.org` and `https://api.vpatlas.org/mapped/columns` both unaffected.
