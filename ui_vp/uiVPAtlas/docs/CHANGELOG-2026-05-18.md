# Changelog — Snapshot 2026-05-18

## v3.5.267 – v3.5.271

### Atlas Visit — "signs of amphibian disease?" question on the Species tab

- **The ask.** Field observers needed a way to flag visible signs of amphibian disease (ranavirus, chytrid, gross deformities) during a pool visit. Added as a question at the bottom of the Species tab, directly above the existing "Fish observed" checkbox.
- **Form.** [survey/visit_create.html](ui_vp/uiVPAtlas/survey/visit_create.html) — new `visitAmphibianDisease` checkbox in the same `.choice-group` as "Fish observed", rendered first so it sits above it. Wired into both the load path (`populateVisitForm`'s checkbox list) and the collect path (`getVisitFormData`'s checkbox list), so the value round-trips through draft save, autosave, and upload exactly like `visitFish`.
- **Database.** New migration [db_migrate/migrations/014_add_visit_amphib_disease.sql](db_migrate/migrations/014_add_visit_amphib_disease.sql) adds `vpvisit."visitAmphibianDisease" boolean DEFAULT false` with a COMMENT documenting intent. Existing rows default to `false`.
- **API.** No code change. The visit services build their column lists at startup via `pgUtil.getColumns('vpvisit', …)`, so the new column flows through `parseColumns` (insert/update) and `whereClause` (filter) automatically once the schema has it — but the running api_vp process had to be force-recreated to re-read the schema (it caches columns at boot). Verified: `/pools/visit` now returns `visitAmphibianDisease` on every row.
- **Visit detail.** [js/visit_card.js](ui_vp/uiVPAtlas/js/visit_card.js) `buildSpeciesTab` renders a new "Amphibian Disease" card (icon `fa-virus`) showing `Signs Observed: Yes/No`, placed immediately before the Fish card to mirror the form's tab order. Only shown when the value is set (matches the Fish card's `!= null && !== ''` guard), so legacy visits that predate the column don't render an empty card.

### Offline — pools + My Visits no longer error offline (the recurring regression, now contracted)

- **The recurring bug.** Data-load code (`pool_list.js loadPools`, `visit_list.html` server fetch) called `fetch()` unconditionally. Offline, the SW returns a synthetic 503; the 503 was thrown and rendered as a red error / dead state instead of silently falling back to cache. This has been reintroduced repeatedly.
- **One portable online check.** New [js/net_status.js](ui_vp/uiVPAtlas/js/net_status.js) exports `isOnline()`: fast-paths the reliable negative (`navigator.onLine === false`), then **confirms** any positive with a guarded `fetch` of `/images/speed-test-small.jpg` (`cache:'no-store'`, cache-buster, 3.5 s `AbortController` timeout — the probe stays in `STATIC_NO_CACHE_PATTERNS` so it always hits the network). Bare `navigator.onLine === true` is not trusted (captive portals / dead Wi-Fi / webviews lie). Result is cached ~4 s so concurrent callers share one probe; resets on the `online` event.
- **visit_list.html.** Server fetch is now gated: offline → skip the fetch entirely, no `serverFetchError`, render local IndexedDB visits only. Online failure still surfaces via the existing diagnostic path.
- **pool_list.js.** `loadPools` returns cache-first as before; the freshness check + `ensureCachesLoaded` now only fire when `isOnline()`. The no-cache path checks connectivity first: offline with no current-key cache falls back to `LEGACY_POOL_CACHE_KEYS` (`pool_cache_v2`, `pool_cache`) so a `POOL_CACHE_KEY` bump doesn't strand an offline user; if nothing is cached at all, a calm grey message replaces the red error.
- **require_online.js.** `ensureOnline()` is now async and delegates to `isOnline()` instead of bare `navigator.onLine`. All four admin call sites updated to `await` (they were already inside `async DOMContentLoaded` handlers).
- **The contract.** New [OFFLINE_CONTRACT.md](OFFLINE_CONTRACT.md) at repo root spells out the one rule, why `navigator.onLine` alone is wrong, the three protected files (app.js / sw_template.js / urlsToCache.js) and what may not change in them, and a required manual offline test. [CLAUDE.md](CLAUDE.md)'s offline section now opens with a loud pointer to it; an auto-memory feedback entry mirrors it.

### Atlas Visit — queue upload no longer silently orphans photos on poor signal

- **The bug.** The visit-queue "Upload" path (`syncVisit` in [survey/js/visit_sync.js](ui_vp/uiVPAtlas/survey/js/visit_sync.js)) set `visit.photos_uploaded = true` *unconditionally* after attempting photo upload. `uploadPhotos()` swallows per-photo network failures and returns a `{uploaded, failed}` count without throwing — so on poor cell service the visit JSON uploaded, every photo `fetch` failed, and the visit was still flagged photos-complete. The queue's "Photos pending" indicator only shows when `photos_uploaded === false` ([survey/js/visit_queue_ui.js:91](ui_vp/uiVPAtlas/survey/js/visit_queue_ui.js#L91)), so it never appeared, no retry was offered, and a green "Visit + N photos uploaded" message lied to the volunteer. The photos survived in IndexedDB but never reached the server — and were lost for good once the volunteer deleted the "done" visit. (The form's own Save & Upload path was already correct — it sets `photos_uploaded = (photoFail === 0)`. This only affected the queue/background-sync path.)
- **The fix.** Both `syncVisit` and `syncPhotosOnly` now set `photos_uploaded = (failed === 0)`, so a partial or total photo failure keeps the flag false — the pending indicator stays lit and the retry path stays live. The status message is now honest about partial failure ("Visit uploaded. 2 of 5 photos sent — 3 pending, retry on WiFi") instead of reporting unqualified success.
- **Second safety net.** The queue Delete button ([survey/js/visit_queue_ui.js](ui_vp/uiVPAtlas/survey/js/visit_queue_ui.js)) now loads the visit and, when `photos_uploaded === false`, swaps the bland "Delete this saved visit?" for an explicit warning that unsent photos exist only on this device and will be permanently lost. Guards against the volunteer-deletes-an-apparently-done-visit loss even if some other path leaves photos pending.

### Review filter — per-visit, on stable signals (the real fix)

- **The bug.** The admin Review filter showed pools that don't need review and hid some that do. Two root causes: (1) it compared pool-wide `max(visit.updatedAt)` vs `max(review.updatedAt)`, which can pair visit-A's edit time against visit-B's review (reviews are tied to a *specific* visit via `vpreview.reviewVisitId`); (2) `updatedAt` on both tables is re-stamped by `trigger_updated_at` on every write — migrations, bulk imports, and a production DB re-instantiation — so the comparison was reading migration noise, not user intent.
- **Why not just fix `updatedAt`.** A codebase grep found four subsystems that depend on `vpvisit`/`vpreview`.`updatedAt` bumping: S123 ESRI delta-sync (`MAX(updatedAt)` high-water mark), insert-vs-update detection (`RETURNING "createdAt"!="updatedAt"`), the admin user-activity rollup (`MAX(vpvisit.updatedAt)` per user), and the dormant `/pools` delta filter. Repurposing `updatedAt` would break those and still leave the comparison migration-tainted. So we use the field that already means the right thing on each side.
- **DB — migration 015** ([db_migrate/migrations/015_backfill_review_qa_date.sql](db_migrate/migrations/015_backfill_review_qa_date.sql)): backfill the 1,293 NULL `vpreview.reviewQADate` rows (all from one 2019-07-25 legacy import) — 1,279 from the linked `vpvisit.visitDate` (real 1930–2013 dates), 14 placeholder/orphan rows from `createdAt::date`. Then `ALTER COLUMN "reviewQADate" SET NOT NULL` so the data-quality gap can't recur and the filter can drop NULL special-casing.
- **DB — migration 016** ([db_migrate/migrations/016_add_visit_last_edited_at.sql](db_migrate/migrations/016_add_visit_last_edited_at.sql)): add nullable `vpvisit."lastEditedAt" timestamp` — **no DEFAULT, no trigger, no backfill**. NULL = "no app-edit since the 2026-05 baseline." `updatedAt` and `trigger_updated_at` are deliberately left untouched so the four subsystems above keep working.
- **API.** [api_vp/vpVisit/vpVisit.service.js](api_vp/vpVisit/vpVisit.service.js) `update()` now appends `, "lastEditedAt" = now()` to the SET clause. `service.update` is reached only via `PUT /pools/visit/:id` (the app's edit path) — S123/bulk-upload use separate upsert services — so this column's sole writer is a genuine user edit. `GET /pools` (`getAll`) already selects `vpvisit.*` and `vpreview.*`, so `lastEditedAt` and `reviewQADate` reach the client with no SELECT change.
- **Client filter.** [explore/js/pool_list.js](ui_vp/uiVPAtlas/explore/js/pool_list.js) dedupe now builds `_visitMap[visitId] = { lastEditedAt, hasReview, maxReviewQADate }` (the `/pools` LEFT JOIN ties each row's review to that row's visit, so this is exact). [explore/js/url_state.js](ui_vp/uiVPAtlas/explore/js/url_state.js) Review case is now: a pool is flagged iff **any** of its visits has no review, OR was user-edited (`lastEditedAt` set) with `lastEditedAt > its newest review's reviewQADate`. Legacy/imported/never-touched reviewed visits have `lastEditedAt = NULL` → not flagged, regardless of migration-tainted `updatedAt`. Old cached rows with no `_visitMap` fall back to "visit exists, no review" until the freshness refetch heals them (no `POOL_CACHE_KEY` bump — per the locked decision).
- **Debug strip updated** to show the new inputs: `e:` newest `lastEditedAt`, `q:` newest `reviewQADate`, `nr:` count of visits with no review. (Still on every pool row; remove once the fix is confirmed in the field.)
